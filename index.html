基本规则 #

SOP 的全部机制都是这五条的展开；执行中有冲突时，以这五条为准。

01
表格即事实源。反馈不在多维表格里 = 不存在。三渠道全量回收，当日 24h 内进表。多维表格沿用现有结构，帖号 / issue 号为共享索引。
02
一条反馈一个 owner。分诊即指派，owner 从跟到关；请假走备份链。owner 为空的条目在每日播报中标红，渠道负责人当场认领。
03
时限驱动。首响：bug 24h · 需求 48h · 咨询当日；P0 一小时内拉人。超时自动进入播报与周报清单，不需要任何人记得。
04
闭环回到用户，且以实测为准。修复 / 结论必须回到原渠道告知用户并请其验证；修没修好以重放不重现为准（§3）。不回话不算已修复；研发说修好了不算，重放过关才算。
05
对账兜底。每日播报核对渠道消息量 vs 表格新增量，周报点名老化条目。漏接率恒为 0 是硬指标，见 §8。

运转总览 · 一条从用户回到用户的闭环 #

反馈的生命周期不是直线流程，而是回路：从用户出发，最终必须回到用户。中间任何一环断掉，都会在每日对账中暴露。

反馈状态机 · 没有可以挂着的中间态 #

状态与多维表格「处理状态」字段一一对应（九个选项，含非问题 / 重复两个出口），五个角色视图各管一段（① 复现 → ⑤ 回流）。每个状态都有明确的执行角色、进入条件和退出的下一步动作。

状态执行角色进入即要做的事退出的下一步
待审核渠道负责人（按渠道）补全字段：渠道 / 原文摘录 / 用户与环境；原始消息链接必填（增量查重锚点）当日内转复现 → 复现中
复现中孟祥雨 + 罗晓阳（复现人字段标注谁做）按线认领：重走复现步骤，填复现状态（可复现 / 无法复现 / 不适用）与复现人，补全环境信息；无法复现按模板追问用户复现完成 → 已确认，等 PM 定级
已确认PM 周旭定级 P0–P3 或拒绝（非问题 / 重复），指派 Dev 负责人、填预计 ETA；P0 直接走快速通道；同时在原渠道首响转 → 开发中
开发中Dev 负责人修复并挂 PR 链接（只挂已合并修复 PR 与在修官方 open PR）；咨询类不进此态，PM 定级时直接答复修复完成 → 待验证
待验证实习生（QA 到岗后主责）按 §3 修复验证执行：对版本、对环境、重放（必现 1 次 / 间歇 ≥3 次），填验收记录不重现 → 待回流；仍重现 → 打回 开发中（Reopened）
待回流线 owner3 天内回原渠道 @用户告知结果与验证方式；回流状态 → 已告知用户确认或代验 → 已修复
已修复cron 自动归档前提：回流状态已告知；小时级自动移入「已修复归档」表；高频问题沉淀进 FAQ / 迁移文档—（周五抽 10% 复查回话质量）

分支与例外

分支从何状态分出规则
P0 快速通道待审核 / 复现中崩溃 / 数据丢失 / 安全 / 大面积不可用 / 迁移严重受阻，任一环节判定即 P0：跳过排队，1h 内周旭 + 复现实习生 + Dev 拉小群，当日给用户阶段性答复。允许先响应后补表，但当天必须补齐登记。
非问题 / 重复已确认（定级）PM 判定非问题或重复也要回话：原渠道说明原因后关闭；重复用「父记录」关联主条目；用户不认同可复议一次。
等用户补充复现中无法复现时按环境模板追问 3 次（复现状态 = 无法复现，状态留复现中）；两周无回应改非问题关闭并告知「随时可重开」。
Reopened 验收打回待验证验收仍重现即打回开发中：优先级不低于原级，验收记录附失败现场让研发直接看到；打回率进周报，衡量修复质量。

修复验证 · 已修复的 bug 必须实测不重现 #

「开发中」转「待验证」只代表研发认为修好了。进入待回流的唯一通道是本节验收：按原始复现信息重放，确认不再重现——研发说修好了不算，重放过关才算。

01
对版本。先确认修复已进入可安装版本，验证环境与提报环境都升到该版本。用户还在旧版本上看到 bug 不算打回，先引导升级再复测。
02
对环境。按登记的复现信息还原环境：OS、CLI / Web 版本、模型、账号与数据。外部报错必须在与提报人等价的环境验证——报错可能来自对方机器，本机不复现不能直接放行。
03
重放。严格按原始复现步骤执行：必现问题重放 1 次，间歇性问题重放 ≥3 次。重放过程留证（截图 / 日志），登记进验证记录。
04
判定。不重现 → 待回流，填验收记录；仍重现 → 打回开发中（Reopened），优先级不低于原级。打回必须附验收记录，让研发直接看到失败现场。
05
沉淀。P0 / P1 修复必须沉淀回归用例，进发版 checklist，每次发版前全量执行。防「修了又坏」；回归用例编号回填反馈表格。

三档验证强度

档位适用验证人要求
自验重放司内可控环境、复现路径清晰实习生（按线认领）按步骤重放，记录环境与结果留证；司内可直接找当事人当面 / 远程验证
用户实测外部报错、环境相关提报用户（实习生引导）回原渠道给验证步骤 + 修复版本，请其升级后复测；用户回复确认才进待回流
回归用例P0 / P1 / 高频路径QA 写用例 · 发版执行人跑用例进回归库，每次发版前全量执行；失败即阻断发版
两个常见误判 —— ① 用户在旧版本上复现：先确认已升级到修复版本，不算打回；② 间歇性 bug 一次没重现就放行：必须重放 ≥3 次全过，并备注「间歇性，观察一个迭代」。

每日节奏 · 三条截止线，每周两次复盘 #

SOP 不靠自觉运转，靠节拍器：每天三条截止线（分流 / 定级 / 接单）+ 每日两扫 + 对账播报，周一排期、周五复盘。

每天三条截止线：15:30 分流完 → 16:30 PM 定级完（定级即指派 Dev）→ 18:00 Dev 接单完；18:00 后进来的新反馈流到明天（次日 15:30 前分流），P0 例外随时处理。
每日节拍 DAILY
  • 10:00机器人
    每日播报：前日新增 / 分诊 / 闭环分产品统计 + 对账（渠道消息量 vs 表格新增）+ 超时与无 owner 标红
  • 12:30渠道负责人
    午扫：飞书群（孟）/ GitHub（罗 + 孟）/ 微信群（周）各扫本渠道，收当天新反馈进表、完成首响；周抽查对不上的渠道
  • 15:30 前渠道负责人
    当天分流截止：新反馈全部进表、复现人分配完；PM 抽查一遍，漏的当场补
  • 16:30 前PM 周旭
    当天定级截止：复现完成的条目定级 P0–P3 / 拒绝，指派 Dev、填 ETA——定级即分工；定不完的注明原因，顺延到次日 10:30 前
  • 18:00渠道负责人 + Dev
    当天接单截止 + 晚扫：当天定级的条目 Dev 确认接收（未接的当晚播报标红）；渠道负责人另过一遍自己名下开发中 / 待验证条目，更新进展或写阻塞原因
  • 18:00 后流到明天
    之后进来的新反馈计入次日批次（次日 15:30 前分流）；复现没做完的自然留在「复现中」次日继续——P0 除外，随时拉群处理
  • 随时周
    P0 电话直达；洪峰模式（10/16–10/23）全员每日 30min 额外分诊，播报加更

度量与五层防漏 · SOP 自己也要被验收 #

「每个反馈都有人跟进」不靠口号，靠五层互相独立的兜底；健康度指标进现有数据看板，周报固定呈现。

指标目标口径与来源
漏接率= 0渠道出现但 24h 未进表的反馈数；来自每日播报对账，硬指标
首响 SLA 达成率≥ 95%bug 24h / 需求 48h / 咨询当日；按周统计
闭环率≥ 90%待验证 → 待回流 → 已修复 转化率，按周统计
回流告知率100%已修复条目必须已回原渠道告知（回流状态 ≥ 已告知）；周五抽检复核
验收打回率≤ 10%待验证验收未通过打回开发中的比例，衡量修复质量；异常升高先查验收环境是否跑偏
P0/P1 回归覆盖100%P0 / P1 修复条目沉淀回归用例的比例；发版前全量执行
>7 天老化数趋势 ↓开发中 / 待回流无动作条目数；周报点名 owner

五层防漏

  • 渠道两扫 —— 每日 12:30 / 18:00 各渠道负责人扫本渠道，第一道人工防线
  • 播报对账 —— 机器人每日核对渠道消息量 vs 表格新增量，差值即疑似漏接
  • 无主标红 —— owner 为空的条目每日播报置顶，渠道负责人当场认领
  • 老化清单 —— 最近动作超 7 天自动进周报，owner 必须给说法
  • 周五抽检 —— 已修复条目抽 10% 复查回话质量，防止"假闭环"

例外与边界 · 不属于这条 SOP 的事怎么办 #

边界外的反馈不是不处理，而是有明确去处——每一条仍然有回话，只是不占用本 SOP 的产能。

情形处理方式
平台 / 商业侧（套餐、支付、退款、账号）不进本 SOP：登记后标记「转出」，回话指路平台团队，跟踪到转出成功即止
情绪 / 吐槽类类型记「咨询」：先安抚回话，指向 FAQ 或迁移文档；若含事实 bug 则拆出单独登记跟进
无法复现的外部 bug按环境模板追问 3 次；仍无法复现转 Pending-user，两周后关闭并告知可随时重开
重复反馈合并到主条目；每条重复也要回一句"已在跟，见 xxx"，不冷落任何人
需求与研发排期冲突线 owner写清冲突点，周一评审会周旭决策；决策结果回话用户（做 / 不做 / 缓做及原因）
非官方渠道的反馈（私聊、别的群）引导到官方渠道（给入口），同时照常登记跟进——渠道是规范，不是门槛
